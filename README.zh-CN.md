# Fermata

用你听不见的信号，让音频设备不进入待机。

[English](README.md) · **简体中文**

Fermata 是一个 Windows 托盘小工具。它持续向音箱、DAC 或蓝牙接收器输出一段听不见的信号，设备因此永远不会判定"已静音足够久"，也就不会关机。

> **名字的来历**：*fermata* 是乐谱上的「延长记号」，意思是把这个音持续得比它本来的时值更长。这正是本工具的手法——把信号一直持住，设备就永远读不到静音。

---

## 要解决的问题

很多音频硬件在静音一段时间后会自行关闭：蓝牙音箱断连、USB DAC 休眠并在唤醒时爆音、Soundbar 切换输入源。其中不少设备的计时器**根本没有关闭开关**。

Marshall Stanmore II 就是这种情况：**静音 20 分钟后进入待机**——这是官方规格，不是经验估值（见 [Marshall 官方支持页](https://www.marshall.com/hk/en/support/speakers/support-for-stanmore-ii-bluetooth/how-to-put-in-standby-mode) 与 [STANMORE II 用户手册](https://www.marshallheadphones.com/on/demandware.static/-/Library-Sites-SharedLibrary-Marshall/default/dwe0dadd06/images/cms-pages/user/Stanmore_II_Full_User_Manual_en_230706.pdf)；待机时所有指示灯熄灭，必须按机身按钮/旋钮或用 Marshall Bluetooth App 才能唤醒）。机身旋钮和官方 App 都没有提供关闭该计时器的设置。Fermata 最初就是为这台音箱写的，但代码里没有任何一处是针对它的。

## 为什么用噪声，而不是超高频正弦

最直觉的做法——放一段没人听得见的 20 kHz 正弦——实际上行不通。这也是随手写的脚本最容易搞错的地方：

| 做法 | 实际会发生什么 |
|---|---|
| **20 kHz 正弦** | 紧贴听觉上限；蓝牙编码器（SBC / aptX）会把靠近 Nyquist 的内容**折叠回可听频段**，变成刺耳的啸叫 |
| **5–20 Hz 正弦** | 会被编码器的高通滤波直接滤掉，根本到不了功放 |
| **数字静音** | 有些设备恰恰以"静音"作为待机判据，这么做等于什么都没做 |
| **宽带噪声**（Fermata 采用） | 无论编码器和设备自身的分频切掉多少，总还有频段携带能量，设备始终能读到信号 |

默认是 **-60 dBFS 的粉红噪声**：在任何真实房间里都听不见，却远高于功放自身的底噪。

### 噪声是怎么生成的

用**十秒循环**：每帧抽一组随机相位频谱，按 `1/sqrt(f)` 塑形，做逆变换，再**环形**重叠相加——所以这个循环天生就是周期的，不存在接缝。运行时回调只做切片；电平已经预先乘进缓冲，回调里一次乘法都没有。

最后这一点是关键。原先每个回调都现场生成一帧，实测 **0.45% 单核**（在真实音频流上用回调内高精度计时测得：回调成本的约 95% 是生成，写入和电平运算几乎不占）。改为切片预生成循环后实测 **0.02%**。测试会验证频谱斜率（−3 dB/octave）、电平、**循环在一个周期后逐字节重复**，以及**接缝处的跳变小于信号本身已有的最大相邻样本跳变**——这才是"没有接缝"的实际含义，而不是一句断言。

电平精确而非近似，靠两个小细节：用正弦窗而非 Hann（50% 重叠下正弦窗平方和恒等于 1，Hann 则在 0.5~1 之间波动）；以及按 Parseval 缩放频谱掩码，使单位方差的随机频谱真的输出单位方差。

更早的版本用 Paul Kellet 单极点滤波器组、逐样本跑在 Python 里——每秒 44 100 次解释器迭代，**9.4% 单核**，对于一个"存在感越低越好"的工具完全不合理。这一路就是从那里开始的。

## 开销

有两件事被实测出来，而且事先都不显然。

**音频不是贵的那部分，而且已经差得很远。** 在作者机器上实测（i7-11700K，16 线程，Windows 11），取 45~60 秒窗口内的进程 CPU 时间：

| 项目 | 实测 |
|---|---|
| CPU，仅音频引擎（无界面） | **0.08~0.10%** 单核（1.0.4 把回调次数减半，见下） |
| CPU，完整程序，仅托盘 | **0.9%** 单核（app 0.24% + WebView2 0.66%） |
| CPU，完整程序，窗口打开 | **约 3%** 单核（app 0.4% + WebView2 2.8%） |

第二、三行要合起来看：**把设置窗口摆在屏幕上，比让它待在托盘里多花约 2% 单核**，而整个程序里最大的几个单项都在那里——WebView2 的 browser 进程（约 1.0%）、renderer（约 0.9%）、GPU 进程（约 0.9%），最后这个只是在画一个静态页面。把窗口隐藏后，renderer 与 GPU 双双降到 0.00%。相比之下音频引擎是 0.1%。

这就是"用 WebView2 做设置窗口"的代价。在决定要什么之前值得知道：这个工具的常态是**一个托盘图标，偶尔打开一次表单**。

| 项目 | 实测 |
|---|---|
| 内存，托盘态 | 工作集约 500 MB——其中 **app 约 130 MB**，**它的 7 个 WebView2 宿主进程约 370 MB** |
| 内存，app 进程私有提交 | 约 570 MB（.NET 运行时预留地址空间，其中只有约 130 MB 是常驻的） |

**工作集不是一个固定属性。** Windows 会在内存紧张时大幅裁剪空闲进程，同一台机器一小时后实测到**合计 140 MB**，代码毫无改动。任务管理器显示的是当前状况；在没人抢占内存时它会稳定在约 500 MB。

这张表最诚实的读法：**开销来自设置窗口，不来自信号。** 如果这个取舍对你不合适，命令行 C++ 工具只有它的十分之一——见下方同类对比。

### 1.0.4：还能压的只剩回调次数

把回调体单独测一遍，16384 帧的 block 里我们自己写的代码只花 **9.7 微秒**（切片 0.22 µs、写两个声道 8.67 µs、每两个 block 算一次 RMS 1.3 µs），折合 **0.0026% 单核**；而整个引擎是约 0.10%。所以贵的不是算术，是 **PortAudio 每次回调的调度**，唯一还能动的杠杆就是「多久调一次」。

在一台**非蓝牙的备用 WASAPI 端点**（48 kHz）上跑真实引擎，两种独立测法：

| block 帧数 | 20 秒内回调次数 | 相对 CPU（周期计数，扣空闲） | 60 秒进程 CPU |
|---|---|---|---|
| 16384（旧） | 73 | 100% | 0.104% |
| **32768（现）** | **37** | **65.0%** | **0.078%** |
| 65536 | 19 | 40.7% | 0.026% * |

\* 0.026% 恰好只是 Windows 15.6 ms CPU 记账的**一个 tick**，落在分辨率边缘，只能读作「明显更低」，不是精确值；不受该粒度影响的 CPU 周期计数才是可信的比值来源。另外这些绝对值来自另一台端点，**不要和上表直接横比**，可信的是同一次测量内部的比值。

**没选 65536**：44.1 kHz 下一个 block 就是 1.49 秒，1.5 秒淡出要跨 3 次回调，停止最坏要 ~4.5 秒（逼近 6 秒 join 超时），5 秒看门狗也只剩 3.4 个回调间隔，而且没在蓝牙端点上验证过。把回调减半已经拿到了大部分收益，停止仍约 3 秒。心跳也从 0.5 秒改成 1 秒：界面本来就每秒刷新一次，多出来的那次唤醒只会把 CPU 从深度 C-state 拉出来。

**请按量级理解**：引擎本来就只有 0.1% 单核，托盘态整机约 0.9% 里大头是 WebView2。这一轮省下的是 0.02~0.03% 单核和一半的定时器唤醒，不会改变上面那张表——它改变的是「这个后台进程有多频繁地打扰 CPU」。

## 快速上手

下载 **[最新 Release](https://github.com/zaxchou/fermata/releases/latest)** 并解压，或[自行构建](#从源码构建)。

然后运行 `Fermata.exe`。

首次启动会打开设置窗口，并立刻开始向设备喂信号。之后：

- **关闭窗口不会退出。** 程序驻留托盘，要真正退出请用托盘菜单里的「退出」。
- **托盘图标颜色就是状态**：绿色＝正在喂信号，琥珀色＝等待中或重连中，红色＝出错，灰色＝已停止。
- 勾上**开机自启**后它会在登录时自行启动，并最小化到托盘。

这是文件夹版，要移动就整个文件夹一起搬。EXE 离不开同目录的 `_internal`，只拷 EXE 是不能用的。

## 设置

| 设置项 | 作用 |
|---|---|
| **输出设备** | 要保活的设备，从列表里按名称选择。选「任意设备（跟随系统默认）」时，解析的是**那一刻**的系统默认输出——详见下方说明。 |
| **名称匹配** | 设备不在上方列表里时改用此项——比如蓝牙音箱尚未配对时。不区分大小写的子串匹配，是纯文本，不是正则。 |
| **信号类型** | 粉红（默认）、白噪、正弦。粉红最稳妥，理由见上。 |
| **频率** | 仅正弦信号使用。 |
| **电平** | −90 至 −20 dBFS。**如果你能听见，就是太响了。** |
| **断线自动重连** | 信号中断后持续重试：设备关机、超出范围等情形。 |
| **重试间隔** | 重试的基础秒数，逐步退避到 60 秒上限。若一段流已健康运行满一分钟，计数会重置。 |
| **等待设备时长** | 启动时等待设备出现的最长时间。`0` 表示一直等待。蓝牙通常在登录后几秒内连上。 |
| **开机自启** | 写入当前用户的 Run 注册表项，指向 EXE。 |
| **启动即开始喂信号** | 启动后不必手动点「开始」。 |
| **启动时最小化到托盘** | 仅在开机自启时生效。 |
| **关闭窗口时最小化到托盘** | 关掉后，点 X 会退出并停止喂信号。 |
| **界面语言** | 「跟随系统」使用 Windows 显示语言，也可固定为 English / 简体中文。立即生效（包括托盘菜单），无需重启。 |

关于电平：该设置决定生成波形的**峰值幅度**，不是 RMS。粉红与白噪因此具有完全相同的 RMS（两者都归一到均匀白噪声），比标称值低 4.8 dB，正弦则高 1.8 dB。换句话说，标称 `−60 dBFS` 的实际 RMS 是 `−64.8 dBFS`。状态页会显示实测 RMS，你随时能看到实际送出去的是什么。

在 Stanmore II 上用 WASAPI loopback 录回端点实测：连续底噪为 **RMS −62.3 dBFS / 峰值 −49.8 dBFS**，会话音量 100% 且未静音。信号确实送达了，但绝对电平非常低——这正是下一节要处理的问题。

关于设备：「任意设备（跟随系统默认）」是在**信号流启动时**解析一次，之后每次重连再解析一次，而不是持续跟随。事后改动 Windows 的默认输出**不会**让信号流迁移过去。这是刻意为之：若真的持续跟随，插上耳机就会抛下这个工具本要保护的音箱。需要知道的后果是：**正在运行的实例喂哪个设备，在启动那一刻就定了**——所以如果你要保护的是一台特定设备，请**按名称明确选中它**，不要留在「任意设备」上。设备索引在每次启动之间是会变的（同一个蓝牙端点一小时前是 `#10`，现在可能是 `#14`），这也是选择结果按名称而非索引保存的原因。

### 文件位置

| 路径 | 说明 |
|---|---|
| `%APPDATA%\Fermata\settings.json` | 设置。可直接手工编辑；未知键会被忽略，超范围的值会被收敛到合法区间。 |
| `%APPDATA%\Fermata\logs\app.log` | 日志。只追加。 |
| `%APPDATA%\Fermata\selftest.txt` | 最近一次 `--selftest` 的报告。 |

另有一个界面上没有的 `sample_rate` 设置（默认 `0` = 使用设备自身的采样率），需要固定采样率时手工改。

## 验证它真的在工作

Fermata 自带一个无界面自检，会跑通整条真实链路：打包资源、设置、设备枚举、自启命令，以及一条真实的音频流。

```powershell
.\Fermata.exe --selftest
```

它会打印通过/失败清单，把报告写进数据目录，且**只有全部通过才返回退出码 0**。这正是它的意义：你不用打开窗口去猜，就能确认产品在你这台机器上确实可用。

要确认设备真的没睡：让程序运行，音量保持在正常水平，等过设备的空闲超时时间，再看它的指示灯或连接状态。**这一步不能省**——`--selftest` 只能证明信号送到了端点，不能证明音箱的待机电路认这笔信号。

## 保活脉冲（1.0.4 引入，1.0.5 起默认关闭）

只推一段听不见的底噪，原来有一个未被验证的假设：设备是依据「有音频流」判断没在闲置，还是依据**解码后的信号电平**？若检测门限高于底噪，界面会一直显示「运行中」、帧数持续增长，音箱却照样在 20 分钟后睡过去——这正是「假功能」最坏的一种形态。1.0.4 因此加了一个可关闭的周期性脉冲：在底噪之上，每 120 秒插入 0.35 秒、−32 dBFS、90 Hz 的低频短音（90 Hz 在等响度曲线上比 1 kHz 低约 25 dB，30 ms 余弦淡入淡出避免咔哒声）。loopback 实测脉冲期间峰值从 **−49 抬到 −29 dBFS（+20 dB）**，周期准确。

**2026-11-04 的实测把这个假设在本机证伪了。** 跑的是 10 月 8 日的老构建——纯 −60 dBFS 粉噪，**没有脉冲、没有看门狗**。Marshall Stanmore II（蓝牙 A2DP）连续静默 **47 分 55 秒**：2875/2875 秒端点 Active、`A2DP SNK` 全程在、Fermata 进程缺席 0 秒、监测数据缺口 0；10 个 5 分钟分段全部为 FLOOR，无一次静音；跨过 20 分钟判定点后用户现场确认音箱仍开着。也就是说 **−49 dBFS 的底噪本身已经足够保活**，脉冲不是必需品。

因此 1.0.5 把 `keepalive_pulse` 默认改为 `false`。脉冲保留为可选配置，只在你确实遇到电平门限更高的设备时才打开。

**发布后的 1.0.5 本身也做了同口径复验（2026-11-04）。** 同一台音箱上，连续静默 **47 分 26 秒**（20:21:16~21:08:42；逐秒记录 2819 条 = 46 分 59 秒），是官方 20 分钟门限的 **2.37 倍**：每一秒都是 FLOOR，底噪峰值中位 −49.7 dBFS；Fermata 缺席 0 秒、`A2DP SNK` 缺失 0 秒、端点非 Active 0 秒、监测数据缺口 0。窗口结束是因为用户放声音检查：**没按任何按钮、没用 App，直接出声成功**，用户现场确认音箱一直醒着。按官方说明，待机后必须靠机身按钮/旋钮或 App 才能唤醒，所以「直接播放成功」是比蓝牙 PnP 存在更强的证据。与老构建的 47 分 55 秒只差 56 秒。

归因仍要收窄：1.0.5 拿到的是**性能与可观测性**（回调次数减半、停滞看门狗、状态页读数），**不是更强的保活能力**。两轮奏效的都是纯 −60 dBFS 粉噪；脉冲全程关闭（PULSE 0 秒），看门狗与重连一次都没触发。

> **边界**：单台设备、每个构建各一次长窗口，不能推广；软件读不到待机电路。本机最硬的证据是「静默约 47 分钟后无需唤醒直接出声」，辅以蓝牙 PnP 全程存在与用户现场观察。脉冲从未被证明有效，所以不该默认启用。

| 设置键 | 默认 | 说明 |
|---|---|---|
| `keepalive_pulse` | `false` | 总开关；设为 `true` 才启用脉冲（默认关闭，见上方实测） |
| `pulse_interval_s` | `120` | 间隔秒数，须远小于设备的待机超时（Stanmore II 是 1200 秒） |
| `pulse_duration_s` | `0.35` | 单次脉冲时长 |
| `pulse_level_dbfs` | `-32` | 峰值电平，合法区间 −70 ~ −20 dBFS |
| `pulse_freq_hz` | `90` | 低频音调，合法区间 30 ~ 500 Hz |

改完 `settings.json` 后重启 Fermata（脉冲缓冲在流启动时构建）。状态页新增两格：**最近输出**（最后一帧距今多久，用来识破「绿色但流已死」）和**保活脉冲**（开/关）。

### 20 分钟 A/B 实测（仅当你的设备仍会待机时才需要做）

1. 音箱开机、音源切到蓝牙、期间不要播放任何音乐或视频，Windows 音量保持日常水平。
2. **保持默认**（`keepalive_pulse: false`），静置 **22 分钟**，看音箱指示灯（待机时全灭）。本机这一步已通过两轮：老构建 47 分 55 秒、1.0.5 为 47 分 26 秒，都远超官方 20 分钟计时。
3. 只有第 2 步真的睡了，才设 `keepalive_pulse: true`、重启 Fermata，再静置 **22 分钟**看灯。
4. 若只有第 3 步保持唤醒，脉冲有效。若**两次都睡**，问题就不在电平，请依次检查：音箱当前音源是否为蓝牙、是否有第二台蓝牙设备抢占了活动音源、Windows/音箱的绝对音量是否过低、以及 Fermata 是否真的还在托盘运行。
5. 若脉冲能听见，把 `pulse_level_dbfs` 往下调 5 dB 再测一轮，找到「刚好有效」的点。

另外，1.0.4 补上了**流停滞看门狗**：帧计数 5 秒不推进就判定流已死并重建，每 10 秒复核端点是否还在。此前蓝牙悄悄掉线时，界面会一直显示「运行中」而无人察觉。

## 与同类工具的比较

这个领域并不空白，有些现成工具比本项目更成熟。这一点必须说清楚：

| 项目 | 说明 |
|---|---|
| [vrubleg/soundkeeper](https://github.com/vrubleg/soundkeeper) | C++，Windows，无界面，可配置项多（含自带噪声模式）。想要完全无界面，这是最成熟的选择。 |

## 从源码构建

```
pip install -r requirements.txt

pyinstaller --noconfirm --clean Fermata.spec
# -> dist\Fermata\
```

需要 Python 3.11 或以上。设置窗口在 Windows 上依赖 WebView2 运行时；Windows 11 和较新的 Windows 10 已内置，否则可从微软单独安装一个小体积组件。

不打包直接运行：

### 测试

三套测试，每一套都隔离到临时数据目录，任何失败都会返回非 0 退出码。两点需要说明：GUI 与 EXE 两套会先停掉正在运行的 Fermata（否则单实例互斥会拒绝被测实例），EXE 那套还会把 Run 注册表项恢复原样。

```
python tests\test_core.py    # 65 项：设置、自启、设备、信号频谱、循环周期性与电平、
                             # 脉冲、跨 block 淡入淡出、引擎生命周期
python tests\test_gui.py     #  9 项：窗口、托盘、日志、单实例互斥
python tests\test_exe.py     # 15 项：打包后的 EXE 验收
```

**默认输出端点是别人的实验对象时，别直接跑测试。** `test_core.py` 的生命周期用例和打包版
`--selftest` 默认会用系统默认输出，也就是往同一台音箱开第二条流，把电平抬高、把测量毁掉。
给它们指定一台备用端点即可（值是设备名的大小写不敏感子串）：

```
set FERMATA_TEST_DEVICE_HINT=KKL
python tests\test_core.py
Fermata.exe --selftest
```

`test_gui.py` 与 `test_exe.py` 会先**停掉所有正在运行的 Fermata**（单实例互斥所需），所以
程序正在保护音箱时不要跑这两套。

`test_exe.py` 需要先打包。它会跑 EXE 自带的 `--selftest`、启动界面、**向窗口真实发送 `WM_CLOSE`** 以证明点 X 是隐藏到托盘而不是杀掉程序，并确认 Run 项已重新指向打包后的 EXE。

`test_core.py` 会直接断言信号本身：实测粉红噪声频谱斜率必须落在 −1.5 至 −4.5 dB/octave 之间，其 RMS 必须与均匀白噪声一致，且真实流出的电平必须与 dBFS 设置相符。

## 一个值得知道的打包坑

如果你用 PyInstaller 打包 pywebview + sounddevice 的程序，可能会踩到。

打包后的 EXE 打不开音频流，报：

```
PortAudioError: Unanticipated host error [PaErrorCode -9999]
WdmSyncIoctl: DeviceIoControl GLE = 0x00000492
```

而同样的源码直接运行却一切正常。根因是：**PortAudio 的 WASAPI 后端要求"打开流的那条线程"自己初始化 COM。** Fermata 在工作线程里推流，而工作线程没有自己的 COM apartment。冻结版对此很严格，源码版则恰好侥幸能用——这是最糟糕的一种 bug 形态，因为它只在打包之后才暴露。

`app/core/engine.py` 在工作线程触碰 PortAudio 之前调用了 `CoInitializeEx(COINIT_MULTITHREADED)`。没有这一句，打包后的程序一个字节都推不出去。

## 已知限制

- **仅限 Windows。** COM 初始化和基于 Run 键的自启都是 Windows 专有，测试也假定在 Windows 上。
- **程序必须确实在运行。** 关闭「开机自启」后，重启或睡眠唤醒都不会让 Fermata 自己回来；这段时间里设备照常进入待机。是否常驻由你决定，程序不会替你改这个设置。日志 `%APPDATA%\Fermata\logs\app.log` 里每次启动都有 `window created`，可用来核对。
- **音量请保持正常水平。** 多数功放在音量控制之前就判断待机，但这一点并非所有厂商都写明，所以"音量旋钮拧到零"属于未验证的情形。
- **设备必须已经配对。** Fermata 会等待端点出现，但不会替你配对蓝牙设备。
- **蓝牙重连受制于操作系统。** Fermata 会等待并重试，但无法强行建立蓝牙协议栈拒绝建立的连接。
